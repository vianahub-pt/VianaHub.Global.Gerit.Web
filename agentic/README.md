# Framework agentic do Gerit Web

Este diretório guarda goals, planos, checkpoints e journal para trabalho local conduzido pelo supervisor PowerShell e processos Codex isolados. Leia `AGENTS.md` e os guardrails antes de iniciar qualquer goal.

## Uso

Execute os scripts pelo PowerShell normal do host, fora do sandbox de uma invocation Codex. O operador inicia `agentic-start.ps1` ou `agentic-loop.ps1`; o supervisor então invoca processos Codex confinados. Não execute gates npm pelo shell do agente. Essa separação é obrigatória porque `npm ci` falhou dentro do sandbox nesta máquina e passou quando autorizado fora dele.

```powershell
.\scripts\agentic-loop.ps1 -Goal "agentic/goals/001-clients-parity.md"
.\scripts\agentic-status.ps1
.\scripts\agentic-resume.ps1
```

No Codex Desktop, uma solicitação natural é convertida conforme `agentic/prompts/front-door.md` em `agentic/state/intake.md`; inicie pelo supervisor com `scripts/agentic-start.ps1`. O start aceita apenas esse artefato, valida metadados, allowlist e working tree antes de Git mutável, cria branch e então grava `agentic/goals/<id>.md`. Na materialização, fixa SHA-256 no state e no evento de provenance do supervisor, além de uma âncora local sob metadados Git fora do sandbox do Codex. Resume/finalização comparam state, journal, âncora e conteúdo; o hash não é inferido nem regenerado a partir de dados editáveis pelo agente. Apenas esse caminho canônico do goal ativo, entregue por `PreparedBranch` autenticado e com hash íntegro, é um bootstrap goal artifact: não exige allowlist/provenance do implementer, entra no commit para auditoria e não pode ser alterado por agentes. Nenhum outro `agentic/goals/**` recebe confiança especial. Não use o intake para transportar outros arquivos. O uso manual de `agentic-loop.ps1 -Goal ...` permanece compatível e não classifica automaticamente o goal como bootstrap. O modo `-PreparedBranch` é interno ao bootstrap. O Desktop mostra progresso de alto nível sem chain-of-thought. Quota/resume continua usando state/journal e `agentic-resume.ps1`; término exige `WAITING_HUMAN_MERGE` ou `FAILED`.

Ao iniciar um goal novo, o supervisor arquiva o checkpoint terminal anterior, grava de uma vez o checkpoint `DISCOVERY` completo com identidade/hash do novo goal e zera os counters. Antes de abrir o handoff, relê e valida state, journal e âncora. O processo filho repete a validação autenticada; um checkpoint antigo, incompleto ou de outro goal continua sendo rejeitado. Resume segue uma rota separada e preserva a identidade, os counters e o journal do goal ativo.

O supervisor PowerShell valida working tree, busca `origin`, cria branch a partir da base declarada e controla state/journal. Ele chama cada role em um processo Codex independente com sandbox próprio: architect faz discovery/planning, somente implementer altera arquivos funcionais permitidos, tester analisa evidência de gates host, e security/reviewer fazem revisões read-only. O supervisor valida o contrato JSON e registra goal, role, invocation ID, timestamp, command fingerprint, exit code, snapshot e artifact sanitizado. Um orchestrator não pode alegar que outras roles executaram. Eventos também registram `controller`, `actor`, `action`, `files_changed` e `result`. Somente o supervisor executa quality gates, valida provenance e, após `READY_TO_COMMIT`, executa `git add`, commit, push da branch e criação/verificação do PR.

O Codex só carrega `.codex/config.toml` em um projeto confiável. O supervisor executa no PowerShell normal do host; cada `codex exec` recebe explicitamente `--sandbox read-only` para architect, tester, security e reviewer, ou `--sandbox workspace-write` para implementer. Não dependa de uma opção de aprovação implícita do runner nem conceda escalonamento de sandbox às roles. O MCP ai-memory local usa `default_tools_approval_mode = "approve"` para operar sem prompt humano. Isso não amplia o sandbox nem autoriza ações destrutivas; não use `danger-full-access`, não permita merge automático e mantenha produção read-only. Merge humano continua obrigatório. `AI_MEMORY_AUTH_TOKEN` é opcional e deve existir somente no ambiente do usuário se a instância exigir autenticação; não grave seu valor no repositório.

Os modelos dos agentes foram conferidos com `codex debug models` no Codex CLI 0.163.0. Orchestrator, implementer e tester usam `gpt-6-luna`; architect, security e reviewer usam `gpt-5.6-terra`. O modelo padrão project-local para `codex exec` sem override também é `gpt-6-luna`, evitando depender de um modelo global que pode não ser suportado pela conta. Revalide os slugs com `codex debug models` ao atualizar o CLI. O CLI instalado rejeitou o override global de concorrência em `[agents]`; por isso não fixamos uma chave incompatível e deixamos a concorrência no padrão do Codex.

## Continuidade e quota

`loop-state.json`, o goal, o plano e `journal/current.md` formam o checkpoint local. Codex CLI não oferece neste fluxo uma API documentada para consultar quota/reset; o supervisor classifica apenas mensagens explícitas capturadas de `codex exec`. Limite desconhecido/temporário usa espera de 15 minutos; mensagem semanal usa 6 horas. Se o processo ou Windows reiniciar, rode `agentic-resume.ps1`; a state machine transiciona o checkpoint ativo para `RESUMING`, preserva a fase pendente, respeita `resume_after` quando houver quota e continua com state e journal existentes. Isso não instala tarefa agendada no Windows.

O supervisor mantém limites de 8 iterações, 40 chamadas e 3 falhas consecutivas no state. A memória é best-effort; se ai-memory estiver parado, journal e plano locais continuam sendo a fonte de verdade. Alterações nos control artifacts são rejeitadas; o supervisor restaura conteúdo regular somente depois de validar que os caminhos não contêm reparse points. Se detectar reparse point, falha fechado sem seguir o caminho nem tentar restaurá-lo.

Resultados JSON de roles em `agentic/state/results/<goal-id>/<invocation-guid>.json` são artefatos locais emitidos pelo supervisor, ficam fora do commit e não bloqueiam um bootstrap posterior quando seguem o caminho canônico. O checkpoint vincula o hash do artefato usado; arquivos com outros formatos de caminho não são aceitos como resultados válidos.

## Responsabilidades Git e encerramento

Dentro de `codex exec`, são proibidos `git fetch`, `git add`, `git commit`, `git push`, `git checkout`/`switch`, criação de PR, merge e alterações em refs Git. Git read-only (`status`, `diff`, `diff --check`, `branch --show-current`, `log`) pode ser usado. Nunca use force push, `reset --hard`, `clean -fd`, push para `develop`/`main`, merge automático ou deploy. Produção permanece read-only e o merge humano continua obrigatório.

O quality gate `diff_check` cobre somente arquivos funcionais commitáveis alterados dentro de `Allowed files`. `agentic/state/**`, `agentic/journal/**` e `agentic/plans/**` são control artifacts locais: não entram no diff funcional nem no commit. Classificações calculadas pelo supervisor: `documentation-only`, `runtime-code` e `runtime-infra`. Para scripts/configurações exclusivas do framework, gates próprios de AST/fixtures são requeridos e gates de aplicação são `NOT_APPLICABLE` com motivo; mudanças de aplicação exigem `npm ci`, lint, typecheck canônico, build e testes aplicáveis. Gates são registrados com comando, classificação, timestamps, duração e exit code. NOT_APPLICABLE nunca significa PASS. Depois de stagear somente os goal paths permitidos, o supervisor revalida paths/classificação/conteúdo e executa `git diff --cached --check` antes do commit.

O supervisor aceita `WAITING_HUMAN_MERGE` somente depois de validar a existência de um PR aberto cujo número, URL, branch de origem e base correspondam ao goal. Ele grava PR e commit no checkpoint/journal. Falhas de commit, push ou PR registram uma causa sanitizada e encerram em `FAILED`, preservando state e alterações locais.

## Autoridade do control plane

O supervisor é o único escritor do state oficial, journal, resultados finais dos quality gates, aprovações de security/reviewer e transições. Cada role retorna apenas seu próprio objeto JSON de `agentic/prompts/autonomous-loop.md`; o supervisor valida schema, role esperada, goal, fase, invocation ID e snapshot. Provenance deriva da invocação feita pelo supervisor, não de uma lista agregada retornada pelo orchestrator. Texto livre ou campos agregados como `role_results` são rejeitados. Falhas persistem diagnóstico sanitizado com operação, invocation/role quando aplicável e checkpoint anterior.

`agentic/journal/current.md` é isolado por goal: cada execução inicia um journal com `goal_id`, branch, base e timestamp; journal anterior é arquivado com nome baseado no goal e hash do conteúdo. Resume falha fechado se identidade de state e journal divergir. `agentic/plans/**` é control artifact local e nunca entra em commit paths. A seleção de runtime prefere PowerShell 7 (`pwsh`) e usa Windows PowerShell 5.1 somente como fallback de compatibilidade; a versão escolhida fica registrada no state.

O supervisor calcula change classification pelos paths commitáveis atuais. Apenas `docs/**/*.md` é `documentation-only`. `runtime-code` exige gates do app. `runtime-infra` executa AST/fixtures do supervisor e só executa gates npm quando os paths afetarem o runtime web, dependências, Docker ou CI. Gates dispensados ficam `NOT_APPLICABLE` com motivo, nunca PASS. O typecheck canônico é `npx tsc --project tsconfig.typecheck.json --noEmit`. Paths, classificação e conteúdo são recalculados após stage; qualquer divergência invalida readiness, e `git diff --cached --check` é executado imediatamente antes do commit.

Front-door exige allowlist concreta antes do handoff. Se o pedido não permitir inferir paths com segurança, faça preflight architect read-only sem intake executável, branch ou Git mutável; só depois de resolver os paths concretos crie o intake. Se permanecer incerto, falhe fechado e peça escopo mais preciso.
